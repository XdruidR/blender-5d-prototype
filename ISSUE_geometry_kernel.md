# Issue Log: Blender 5D Prototype — IFC, MCP, Geometry Kernel

## 1. Geometry Kernel Crash (UNRESOLVED on Windows — likely platform-specific)

### Error
```
RuntimeError: Type held at index 8 is class Blank and not class IfcUtil::IfcBaseClass * __ptr64
```

Occurs in `ifcopenshell.geom.create_shape()` and `ifcopenshell.geom.iterator` for IFC files **generated by ifcopenshell**.
Revit-generated IFC files (`blender-bim/BRIDGES_5D.ifc`) load geometry successfully on the same machine.
Minimal hand-crafted IFC (no ShapeBuilder, no api.run) also fails — so it's not our pipeline code.
Confirmed: platform-specific bug in ifcopenshell 0.8.5 C++ SWIG bindings on Windows/Python 3.13
when processing self-generated IFC files. Linux expected to work.

### Environment
- Blender 5.1.1 + Bonsai (ifcopenshell 0.8.5)
- Python 3.13 / Windows 11
- All four geometry libraries fail: `opencascade`, `cgal`, `cgal-simple`, `hybrid-cgal-simple-opencascade`

### What works
- `ifcopenshell.open()` — OK
- Reading entities, psets, attributes — OK
- `bpy.ops.bim.load_project()` returns `{'FINISHED'}` but 0 objects created — geometry step crashes silently

### What was tried
- `IfcArbitraryClosedProfileDef` → `IfcRectangleProfileDef` — no effect
- Removed `IfcGeometricRepresentationSubContext` derived `*` attrs — no effect
- ifcopenshell 0.8.4.post1 — same error
- Minimal single-element IFC — same error

### Workaround (ADOPTED)
Build Blender meshes directly in Python from known dimensions — bypass the geometry kernel entirely.
Known dims for prototype: `COL_W=0.4`, `BEAM_W=0.3`, `BEAM_D=0.5`, `SLAB_T=0.2`, `FTG_SIZE=1.2`, `SPACING=6.0`, `STOREY_H=3.5`.
Attach IFC entity references as Blender custom properties. All `Pset_5D` data still readable via `ifcopenshell.open()`.

### Root cause
Windows/Python 3.13 SWIG binding mismatch. Not reported on Linux.
Try Linux for HIGH CONFIDENCE fix: `pip install ifcopenshell numpy python-dateutil`.

## 3. Hardcoded Paths Break on New Machine (RESOLVED)

### Error
```
FileNotFoundError: [Errno 2] No such file or directory: 'C:\Users\ANDRES\dev\blender-bim\data\pv_spread.json'
```

### Cause
`wbs_panel.py` had absolute paths pointing to original dev machine (`ANDRES`).

### First fix attempt (wrong)
Used `os.path.dirname(os.path.abspath(__file__))` — fails in Blender because `__file__` resolves to a path *inside* the `.blend` file:
```
C:\Users\AndresR\Dev\blender-bim\GRB_WBS2.blend\wbs_panel.py
```

### Final fix (correct)
Use `bpy.data.filepath` to locate the `.blend` file, then derive repo root from that:
```python
_BASE = os.path.dirname(os.path.abspath(bpy.data.filepath))

IFC_PATHS      = [os.path.join(_BASE, "BRIDGES_5D.ifc")]
PV_SPREAD_PATH = os.path.join(_BASE, "data", "pv_spread.json")
GANTT_HTML     = os.path.join(_BASE, "gantt.html")
```
Script now portable — works on any machine as long as `.blend` file is in repo root.

## 5. Bonsai `blenderbim` Module Not Accessible via MCP (KNOWN LIMITATION)

Bonsai's `blenderbim` Python module is only available inside Blender's own Python runtime.
When scripting via blender-mcp (which executes code in Blender's Python), `blenderbim` is accessible.
When scripting via standalone Python or Claude Code shell, it is not.

**Rule:** All IFC read/write uses standalone `ifcopenshell` (pip-installable).
`blenderbim`/Bonsai operators (`bpy.ops.bim.*`) only called from scripts run inside Blender.
